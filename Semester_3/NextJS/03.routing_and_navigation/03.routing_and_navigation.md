# 03. Routing and Navigation

Next.js uses **file-based routing**. This means the folder and file structure of the application determines the URLs of the application.

This covers routing and navigation in the **App Router**.

> The Pages Router also uses file-based routing, but its route conventions are different. The App Router is the recommended router for new projects.

---

# 1. File-Based Routing

In the App Router, routes are created inside the `app/` directory.

A folder represents a URL segment, and a `page.tsx` file makes that segment accessible as a route.

```text
app/
├── page.tsx
├── about/
│   └── page.tsx
└── products/
    └── page.tsx
```

This creates:

```text
/          → app/page.tsx
/about     → app/about/page.tsx
/products  → app/products/page.tsx
```

> A folder alone does not create a public route. The route normally needs a `page.tsx` file.

---

## Static Routes

A static route has a fixed URL.

Example:

```text
app/
├── page.tsx
├── about/
│   └── page.tsx
└── contact/
    └── page.tsx
```

Routes:

```text
/          → Home
/about     → About
/contact   → Contact
```

Static routes are useful for pages such as:

```text
/about
/contact
/pricing
/terms
```

---

## Nested Routes

Routes can be nested by creating folders inside other route folders.

```text
app/
└── dashboard/
    ├── page.tsx
    └── settings/
        └── page.tsx
```

Routes:

```text
/dashboard
/dashboard/settings
```

Nested routes are useful when an application has sections and subsections.

For example:

```text
/dashboard
/dashboard/profile
/dashboard/settings
/dashboard/billing
```

---

## Dynamic Routes

Dynamic routes are used when part of the URL changes.

Use square brackets:

```text
[id]
```

Example:

```text
app/
└── products/
    └── [id]/
        └── page.tsx
```

This route can match:

```text
/products/1
/products/25
/products/100
```

---

### Route Parameters

**Route parameters** are values taken from **dynamic URL segments** — the parts of the path defined by folders like `[id]` or `[slug]`.

```text
URL: /products/25
App Router file: app/products/[id]/page.tsx
Pages Router file: pages/products/[id].tsx
Route parameter: id = "25"
```

Route parameters are part of the **path**, not the query string.

Route parameters identify **which resource** the page is showing.

How you read route parameters depends on the router and whether the code runs on the server or the client.

| Router       | Server-side                                                 | Client-side                                         |
| ------------ | ----------------------------------------------------------- | --------------------------------------------------- |
| App Router   | `params` prop on the page                                   | `useParams()` from `next/navigation`                |
| Pages Router | `context.params` in `getServerSideProps` / `getStaticProps` | `router.query` via `useRouter()` from `next/router` |

#### App Router — Server Component

In the App Router, a Server Component page receives **`params`** as a prop:

```text
Route file: app/products/[id]/page.tsx
URL: /products/25
```

```tsx
// app/products/[id]/page.tsx

type Props = {
	params: Promise<{ id: string }>;
};

export default async function ProductPage({ params }: Props) {
	const { id } = await params;

	return <p>Product ID: {id}</p>;
}
```

#### App Router — Client Component

When a Client Component needs route parameters, use the `useParams` hook from `next/navigation`:

```tsx
"use client";

import { useParams } from "next/navigation";

export default function ProductDetails() {
	const params = useParams();
	const id = params.id;

	return <p>Product ID: {id}</p>;
}
```

#### Pages Router — Server-side

In the Pages Router, dynamic route files live in `pages/` — for example `pages/products/[id].tsx`.

Server-side data functions receive route parameters through the **`context.params`** object:

```tsx
// pages/products/[id].tsx

export async function getServerSideProps(context) {
	const { id } = context.params;

	return {
		props: { id },
	};
}

export default function ProductPage({ id }) {
	return <p>Product ID: {id}</p>;
}
```

`getServerSideProps()` runs on the server for each request. The same `context.params` object is available in `getStaticProps()` for statically generated dynamic routes.

#### Pages Router — Client-side

In a page component on the client, read route parameters with **`useRouter`** from `next/router`:

```tsx
import { useRouter } from "next/router";

export default function ProductDetails() {
	const router = useRouter();
	const { id } = router.query;

	return <p>Product ID: {id}</p>;
}
```

> In the Pages Router, import `useRouter` from `next/router`. In the App Router, import it from `next/navigation`.

---

### Search Parameters

**Search parameters** (also called **query parameters**) appear **after** `?` **in the URL**.

```text
/products?search=phone&page=2
          ↑
          search parameters
```

In this example:

```text
search = "phone"
page = "2"
```

Search parameters are useful for:

```text
Filtering   → /products?category=phones
Pagination  → /products?page=2
Sorting     → /products?sort=price
Searching   → /products?search=iphone
```

They are different from **route parameters**, which identify a specific resource in the path.

How you read search parameters depends on the router and whether the code runs on the server or the client.

| Router       | Server-side                                                | Client-side                                         |
| ------------ | ---------------------------------------------------------- | --------------------------------------------------- |
| App Router   | `searchParams` prop on the page                            | `useSearchParams()` from `next/navigation`          |
| Pages Router | `context.query` in `getServerSideProps` / `getStaticProps` | `router.query` via `useRouter()` from `next/router` |

#### App Router — Server Component

In the App Router, a Server Component page receives **`searchParams`** as a prop:

```text
Route file: app/products/page.tsx
URL: /products?search=phone&page=2
```

```tsx
// app/products/page.tsx

type Props = {
	searchParams: Promise<{
		search?: string;
		page?: string;
	}>;
};

export default async function ProductsPage({ searchParams }: Props) {
	const { search, page } = await searchParams;

	return (
		<div>
			<p>Search: {search ?? "none"}</p>
			<p>Page: {page ?? "1"}</p>
		</div>
	);
}
```

For `/products?search=phone&page=2`:

```text
search = "phone"
page = "2"
```

#### App Router — Client Component

When a Client Component needs search parameters, use the `useSearchParams` hook from `next/navigation`:

```tsx
"use client";

import { useSearchParams } from "next/navigation";

export default function ProductsFilters() {
	const searchParams = useSearchParams();

	const search = searchParams.get("search");
	const page = searchParams.get("page");

	return (
		<div>
			<p>Search: {search ?? "none"}</p>
			<p>Page: {page ?? "1"}</p>
		</div>
	);
}
```

For `/products?search=phone&page=2`:

```text
search = "phone"
page = "2"
```

> Wrap components that use `useSearchParams()` in a `<Suspense>` boundary when needed, because reading search params can defer rendering during static generation.

#### Pages Router — Server-side

In the Pages Router, server-side data functions receive search parameters through the **`context.query`** object:

```tsx
// pages/products/index.tsx

export async function getServerSideProps(context) {
	const { search, page } = context.query;

	return {
		props: {
			search: search ?? null,
			page: page ?? "1",
		},
	};
}

export default function ProductsPage({ search, page }) {
	return (
		<div>
			<p>Search: {search ?? "none"}</p>
			<p>Page: {page}</p>
		</div>
	);
}
```

`getServerSideProps()` runs on the server for each request. The same `context.query` object is available in `getStaticProps()` when query values are known at build time.

#### Pages Router — Client-side

In a page component on the client, read search parameters with **`useRouter`** from `next/router`:

```tsx
import { useRouter } from "next/router";

export default function ProductsFilters() {
	const router = useRouter();
	const { search, page } = router.query;

	return (
		<div>
			<p>Search: {search ?? "none"}</p>
			<p>Page: {page ?? "1"}</p>
		</div>
	);
}
```

For `/products?search=phone&page=2`:

```text
router.query.search = "phone"
router.query.page = "2"
```

> In the Pages Router, `router.query` can contain both route parameters and search parameters. On dynamic routes such as `pages/products/[id].tsx`, read only the query keys you need.

#### Route parameters vs search parameters

|                           | Route parameters                | Search parameters                |
| ------------------------- | ------------------------------- | -------------------------------- |
| **Where**                 | In the URL path                 | After `?` in the URL             |
| **Example**               | `/products/25`                  | `/products?search=phone&page=2`  |
| **Often used for**        | Identifying a specific resource | Filters, pagination, sorting     |
| **Defined by**            | Dynamic folders like `[id]`     | Query string keys like `?page=2` |
| **App Router (server)**   | `params` prop                   | `searchParams` prop              |
| **App Router (client)**   | `useParams()`                   | `useSearchParams()`              |
| **Pages Router (server)** | `context.params`                | `context.query`                  |
| **Pages Router (client)** | `router.query` (path keys)      | `router.query` (query keys)      |
| **Current pathname**      | `usePathname()`                 | —                                |

Simple rule:

```text
/products/25           → route parameter (product id = 25)
/products?search=phone → search parameter (search = phone)
```

## Catch-All Routes

A catch-all route uses:

```text
[...slug]
```

It can match multiple URL segments.

Example:

```text
app/
└── docs/
    └── [...slug]/
        └── page.tsx
```

It can match:

```text
/docs/react
/docs/react/hooks
/docs/react/hooks/use-state
```

The route parameter contains the matched segments.

For example:

```text
/docs/react/hooks
```

can produce:

```ts
slug = ["react", "hooks"];
```

Catch-all routes are useful for structures such as:

- Documentation
- Categories
- Nested content
- Multi-level paths

**Real-world examples:**

- **Documentation sites** — A docs platform may serve pages like `/docs/react/hooks/use-state` or `/docs/nextjs/routing/dynamic-routes`. One catch-all route under `/docs/[...slug]` can render any depth of documentation without creating a separate file for every page.

- **E-commerce category browsing** — An online store might use paths such as `/shop/electronics/phones/android` or `/shop/clothing/men/shirts`. A catch-all route lets shoppers drill down through nested categories while the app reads all segments from the URL to filter products.

- **Help centers and knowledge bases** — Support sites often organize articles under paths like `/help/account/billing/refunds` or `/help/shipping/international/customs`. One route can look up the correct article based on the full path.

- **Blog or news archives** — A publication might structure content as `/blog/2024/january/understanding-nextjs-routing`. The year, month, and slug can all come from a single catch-all segment list.

- **CMS or portfolio sites** — A marketing site built from a content manager may expose pages like `/work/branding/acme-campaign` or `/services/consulting/strategy`. Catch-all routing allows editors to add nested pages without developers creating new route files each time.

- **Developer platforms** — API reference sites commonly use paths such as `/reference/payments/create-charge` or `/reference/users/update-profile`, where each extra segment represents a deeper section of the documentation tree.

---

## Optional Catch-All Routes

An optional catch-all route uses:

```text
[[...slug]]
```

The difference is that the route can also match the parent path without any additional segment.

Example:

```text
app/
└── docs/
    └── [[...slug]]/
        └── page.tsx
```

This can match:

```text
/docs
/docs/react
/docs/react/hooks
```

Use optional catch-all routes when both the base route and deeper paths should be handled by the same route structure.

**Real-world examples:**

- **Documentation home and nested pages** — A docs site may need `/docs` to show an overview while also serving `/docs/react/hooks/use-state` for individual articles. An optional catch-all route handles the docs landing page and every deeper page with one route structure.

- **Shop landing and category pages** — An e-commerce site might use `/shop` as the main store page and `/shop/electronics/phones` for nested browsing. The same route can show featured products at the root and filtered results when more segments are present.

- **Help center index and articles** — A support site can serve `/help` as a searchable help hub and `/help/account/billing/refunds` for specific guides, without maintaining separate routes for the index and the nested content.

- **Blog listing and archived posts** — A blog may expose `/blog` as the main listing and `/blog/2024/january/nextjs-routing` for individual posts organized by date, all rendered through one flexible route.

- **Portfolio overview and project details** — A creative portfolio might use `/work` to showcase all projects and `/work/branding/acme-campaign` for case-study pages, letting the same layout adapt based on whether a slug is present.

- **File or media browsers** — A cloud storage app could serve `/files` as the root folder view and `/files/projects/designs/logo.png` for deeper paths, using one route to decide whether to show a folder listing or file content.

---

## When to Use Catch-All vs Optional Catch-All Routes

Both route types handle URLs with multiple nested segments. The choice depends on whether the **parent path itself** also needs to be a valid route.

| Question                                    | Use `[...slug]`                                 | Use `[[...slug]]`                               |
| ------------------------------------------- | ----------------------------------------------- | ----------------------------------------------- |
| Should `/docs` work on its own?             | No — only `/docs/...` with at least one segment | Yes — `/docs` and `/docs/...` both work         |
| Is there a separate page for the base path? | Yes — usually `docs/page.tsx` handles `/docs`   | No — one route handles everything under `/docs` |
| URL must always have extra segments?        | Yes                                             | No                                              |

### Use a catch-all route `[...slug]` when

- The base path already has its own dedicated route file.
- Nested paths always contain **at least one extra segment** after the parent.
- You want a clear separation between the section homepage and deeper pages.

Example setup:

```text
app/docs/page.tsx              → /docs
app/docs/[...slug]/page.tsx    → /docs/react, /docs/react/hooks
```

Use this when `/docs` should show a fixed landing page, and only deeper paths like `/docs/react/hooks` should be handled by the catch-all route.

### Use an optional catch-all route `[[...slug]]` when

- The base path and all nested paths should share the **same route logic**.
- You do not want to maintain a separate `page.tsx` for the parent folder.
- The page should adapt based on whether slug segments exist or not.

Example setup:

```text
app/docs/[[...slug]]/page.tsx  → /docs, /docs/react, /docs/react/hooks
```

Use this when `/docs` might show a docs index, and deeper paths render articles from the same component by reading how many slug segments were matched.

### Simple decision rule

```text
Need /docs and /docs/... in one route?     → [[...slug]]
Need /docs separate from /docs/...?        → page.tsx + [...slug]
```

If the parent URL should always exist as its own page with different content or layout from nested pages, use a **catch-all route** with a separate parent `page.tsx`.

If the parent URL is just the top level of the same nested structure, use an **optional catch-all route**.

## Route Group

Route groups allow you to organize routes without adding the folder name to the URL.

They use parentheses:

```text
(marketing)
```

Example:

```text
app/
├── (marketing)/
│   ├── page.tsx
│   └── pricing/
│       └── page.tsx
│
└── (dashboard)/
    └── dashboard/
        └── page.tsx
```

The group names do not appear in the URL.

```text
app/(marketing)/pricing/page.tsx
                ↓
             /pricing
```

Route groups are useful for:

- Organizing large applications
- Separating application sections
- Applying different layouts to different sections

For example:

```text
(marketing)
    ↓
Marketing layout

(dashboard)
    ↓
Dashboard layout
```

---

## Private Folders

Private folders use an underscore:

```text
_folder
```

They are not considered route segments.

Example:

```text
app/
├── dashboard/
│   ├── page.tsx
│   └── _components/
│       └── Chart.tsx
```

`_components` is not treated as a route.

So:

```text
/dashboard
```

exists, but:

```text
/dashboard/_components
```

is not created as a route from that folder.

Private folders are useful for keeping route-specific files and components close to the route without making them part of the URL structure.

---

#### Reading the current pathname — `usePathname()`

To read the current URL path in a Client Component — for example, to highlight the active nav link — use `usePathname`:

```tsx
"use client";

import Link from "next/link";
import { usePathname } from "next/navigation";

export default function Navbar() {
	const pathname = usePathname();

	return (
		<nav>
			<Link href='/' className={pathname === "/" ? "active" : ""}>
				Home
			</Link>
			<Link
				href='/products'
				className={pathname.startsWith("/products") ? "active" : ""}
			>
				Products
			</Link>
		</nav>
	);
}
```

On `/products`, `pathname = "/products"`.

# 2. Navigation

## Navigation with `<Link>`

Next.js provides the `Link` component for navigation between routes.

Import it from:

```tsx
import Link from "next/link";
```

Example:

```tsx
import Link from "next/link";

export default function Navbar() {
	return (
		<nav>
			<Link href='/'>Home</Link>
			<Link href='/about'>About</Link>
			<Link href='/products'>Products</Link>
		</nav>
	);
}
```

`Link` enables client-side navigation instead of requiring a full browser page reload.

Next.js can also prefetch linked routes when appropriate, which can make navigation feel faster.

### Prefer `<Link>` for normal navigation

Use:

```tsx
<Link href='/products'>Products</Link>
```

instead of manually handling a click when the purpose is simply to navigate to another page.

---

## Programmatic Navigation

Sometimes navigation needs to happen after an action rather than after clicking a normal link.

Examples:

```text
Successful login
Form submission
Logout
Save operation
```

For these situations, Next.js provides programmatic navigation.

---

### `useRouter`

`useRouter` allows a **Client Component** to navigate programmatically.

Import it from:

```tsx
import { useRouter } from "next/navigation";
```

Example:

```tsx
"use client";

import { useRouter } from "next/navigation";

export default function LoginForm() {
	const router = useRouter();

	function handleLogin() {
		// login logic

		router.push("/dashboard");
	}

	return <button onClick={handleLogin}>Login</button>;
}
```

Common methods:

```tsx
router.push("/dashboard");
router.replace("/dashboard");
router.back();
router.refresh();
router.prefetch("/dashboard");
```

### `router.push()`

Navigates to a new URL.

```tsx
router.push("/dashboard");
```

The current history entry is preserved.

### `router.replace()`

Navigates to a new URL without adding a new history entry.

```tsx
router.replace("/dashboard");
```

This is useful when the user should not return to the previous page using the browser Back button.

### `router.back()`

Moves back in browser history.

```tsx
router.back();
```

### `router.refresh()`

Refreshes the current route and requests updated server-rendered data without performing a full browser reload.

```tsx
router.refresh();
```

### `router.prefetch()`

Manual prefetches a route in the background so navigation to that page can feel faster later.

```tsx
router.prefetch("/dashboard");
```

This pairs naturally with `<Link>`, which can prefetch routes automatically when appropriate.

> `useRouter` is a Client Component hook. Use it when navigation needs to happen because of a client-side action.

---

### `redirect()`

Sometimes the application needs to redirect a user automatically.

Next.js provides the `redirect()` function.

```tsx
import { redirect } from "next/navigation";

export default async function DashboardPage() {
	const isLoggedIn = false;

	if (!isLoggedIn) {
		redirect("/login");
	}

	return <h1>Dashboard</h1>;
}
```

This is useful for cases such as:

```text
Not authenticated
       ↓
/login

Authenticated
       ↓
/dashboard
```

`redirect()` can be used in server-side rendering contexts such as Server Components, Route Handlers, and Server Actions.

For navigation triggered by a client-side event handler, use `useRouter()` instead.

> `redirect()` **throws internally** and must be called outside `try/catch` — otherwise the redirect is swallowed.

---

# 3. Choosing the Right Navigation Method

Use the method based on what you are trying to do.

| Situation                                                  | Recommended         |
| ---------------------------------------------------------- | ------------------- |
| User clicks a normal navigation link                       | `<Link>`            |
| Navigate after a client-side action                        | `useRouter()`       |
| Redirect during server-side logic                          | `redirect()`        |
| Read route parameters in App Router Server Component page  | `params` prop       |
| Read route parameters in App Router Client Component       | `useParams()`       |
| Read route parameters in Pages Router (server)             | `context.params`    |
| Read route parameters in Pages Router (client)             | `router.query`      |
| Read current pathname in Client Component                  | `usePathname()`     |
| Read URL search parameters in App Router Client Component  | `useSearchParams()` |
| Read search parameters in App Router Server Component page | `searchParams` prop |
| Read search parameters in Pages Router (server)            | `context.query`     |
| Read search parameters in Pages Router (client)            | `router.query`      |

# Summary

- Next.js uses **file-based routing**.
- The App Router uses the `app/` directory.
- `page.tsx` creates a route.
- Static routes use fixed folder names.
- Nested routes are created by nesting folders.
- Dynamic routes use `[param]`.
- Route parameters come from dynamic URL segments such as `/products/25`.
- Search parameters come after `?` in the URL, such as `/products?search=phone&page=2`.
- Catch-all routes use `[...param]`.
- Optional catch-all routes use `[[...param]]`.
- Route groups use `(group)` and do not appear in URLs.
- Private folders use `_folder` and are excluded from routing.
- Use `params` in App Router Server Components and `useParams()` in App Router Client Components to read route parameters.
- In the Pages Router, use `context.params` in `getServerSideProps` / `getStaticProps` on the server and `router.query` via `useRouter()` from `next/router` on the client.
- Use `searchParams` in App Router Server Components and `useSearchParams()` in App Router Client Components to read search parameters.
- In the Pages Router, use `context.query` in `getServerSideProps` / `getStaticProps` on the server and `router.query` via `useRouter()` from `next/router` on the client.
- Use `usePathname()` to read the current pathname in a Client Component.
- Use `<Link>` for normal navigation.
- Use `useRouter()` for client-side programmatic navigation.
- Use `redirect()` when navigation should happen as part of server-side logic.

> **Simple rule:** Use the file system to define routes, `<Link>` for normal navigation, and programmatic navigation APIs only when navigation depends on application logic.
