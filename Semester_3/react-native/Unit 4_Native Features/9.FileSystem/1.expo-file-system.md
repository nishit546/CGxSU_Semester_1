# Expo File System (`expo-file-system`)

---

# Introduction

Modern mobile applications do much more than display information on the screen.

A real-world application often needs to **store, retrieve, organize, modify, download, upload, and manage files**.

For example:

- A Notes application needs to save notes.
- A Gallery application works with images and videos.
- A PDF reader needs to access PDF documents.
- A Download Manager needs to store downloaded files.
- A Chat application may need to download images, videos, documents, and other attachments.
- A Profile application may need to store profile images temporarily.
- An offline application may need to download data and files so they can be accessed without an internet connection.
- An application may need to create local JSON files for structured information.

All of these use cases involve **files and storage**.

React Native applications can use Expo's `expo-file-system` library to work with files and directories available to the application.

## What is `expo-file-system`?

`expo-file-system` provides APIs for accessing and managing files and directories on the device.

It supports concepts such as:

```text
Create
Read
Write
Copy
Move
Delete
List
Download
Upload
```

A simplified view is:

```text
React Native Application
           │
           ↓
     expo-file-system
           │
           ↓
     Device File System
```

The library gives application code a structured way to work with files and directories without requiring us to hard-code platform-specific storage paths.

> **Important:** The file system is not the same thing as React state, AsyncStorage, SecureStore, or a database. Each solves a different problem.

---

# Why Learn File System?

Before learning the API, understand **why a file system is needed**.

Consider:

```tsx
const [name, setName] = useState("");
```

The `name` value is stored in React state.

For example:

```text
User enters:
Raj

React state:
name = "Raj"
```

React state is mainly used for the application's current UI state.

It is not the same thing as persistent file storage.

If an application needs to store:

- a PDF
- an image
- a video
- a text file
- a JSON file
- a downloaded document

then a file-based storage mechanism can be appropriate.

### React State vs File System

```text
React State
    ↓
"What is happening in the UI right now?"

File System
    ↓
"What files does the application need to store/manage?"
```

They can work together:

```text
File System
     ↓
Read file
     ↓
Application Logic
     ↓
React State
     ↓
UI
```

# Part 1 — File System Fundamentals

Before writing Expo File System code, understand the terminology.

---

## 1.1 What is a File?

A **file** is a container used to store data.

Examples:

```text
notes.txt
profile.json
photo.jpg
resume.pdf
video.mp4
```

A file name may contain:

```text
resume.pdf
│      │
│      └── Extension
└───────── Name
```

The extension generally indicates the expected format, but the extension alone should not be treated as authoritative.

---

## 1.2 File Name

A file has a name that identifies it within its directory.

```text
Documents/
├── resume.pdf
├── notes.txt
└── profile.jpg
```

Two files can have the same name if they are in different directories:

```text
Documents/
└── notes.txt

Downloads/
└── notes.txt
```

Therefore:

> **A file's identity is not just its name; its location also matters.**

---

## 1.3 File Extension

The extension is the part after the final dot.

```text
notes.txt
     ↑
    .txt
```

Common extensions:

| Extension | Common purpose |
|---|---|
| `.txt` | Plain text |
| `.json` | Structured JSON |
| `.jpg` | Image |
| `.png` | Image |
| `.pdf` | Document |
| `.mp4` | Video |
| `.csv` | Tabular data |

---

## 1.4 What is a Directory?

A **directory** is commonly called a **folder**.

It organizes files and other directories.

```text
Documents/
│
├── resume.pdf
├── notes.txt
└── profile.jpg
```

Here:

```text
Documents → Directory
resume.pdf → File
notes.txt → File
profile.jpg → File
```

---

## 1.5 Directories Can Be Nested

Directories can contain other directories.

```text
Documents/
│
├── Personal/
│   ├── resume.pdf
│   └── profile.jpg
│
└── College/
    ├── assignment.pdf
    └── notes.txt
```

This creates a hierarchy:

```text
Documents
   │
   ├── Personal
   │     ├── resume.pdf
   │     └── profile.jpg
   │
   └── College
         ├── assignment.pdf
         └── notes.txt
```

---

## 1.6 File vs Directory

| File | Directory |
|---|---|
| Stores data | Organizes items |
| Represents one file | Represents a folder |
| Example: `notes.txt` | Example: `notes/` |
| Can be read/written | Can be listed/managed |
| Has file metadata | Has directory metadata |

Mental model:

```text
Directory
    ↓
Contains
    ↓
Files and Directories
```

---

## 1.7 What is a Path?

A **path** describes the location of a file or directory.

Example:

```text
Documents/notes/note.txt
```

Step by step:

```text
Documents
    ↓
notes
    ↓
note.txt
```

The path tells the system where the resource is located.

---

## 1.8 Path as an Address

Think of a physical address:

```text
Country
   ↓
City
   ↓
Street
   ↓
House
```

A file path can be thought of as:

```text
Root/Location
      ↓
Directory
      ↓
Subdirectory
      ↓
File
```

Example:

```text
Documents/Projects/ReactNative/app.json
```

---

## 1.9 Absolute Path vs Relative Path

### Relative Path

A relative path describes a location relative to another location.

```text
notes/note.txt
```

### Absolute Path

An absolute path describes a complete location from a root.

Conceptually:

```text
/root/Documents/notes/note.txt
```

On mobile platforms, physical paths are platform-dependent.

> Do not hard-code guessed Android or iOS paths. Use Expo APIs such as `Paths`.

---

## 1.10 What is a URI?

URI stands for:

> **Uniform Resource Identifier**

A URI identifies a resource.

A file may have a URI similar to:

```text
file:///.../Documents/profile.jpg
```

Mental model:

```text
File
 ↓
URI
 ↓
Reference to the resource
```

Common URI schemes you may encounter include:

```text
file://
http://
https://
content://
```

Their meaning depends on the API and platform.

---

## 1.11 Path vs URI

Path and URI are related but should not be treated as exactly the same.

### Path

Primarily describes a location:

```text
Documents/images/profile.jpg
```

### URI

Identifies a resource:

```text
file:///.../Documents/images/profile.jpg
```

Simplified mental model:

```text
Path
 ↓
Location

URI
 ↓
Resource reference
```

---

## 1.12 What is Storage?

Storage is where data is kept.

A simplified mobile model:

```text
Mobile Device
│
├── Application A
│   └── App Storage
│
├── Application B
│   └── App Storage
│
└── Application C
    └── App Storage
```

Applications operate within storage areas available to them under platform rules.

---

## 1.13 Application Storage

Conceptually:

```text
My Application
│
└── App Storage
    │
    ├── Documents
    │   ├── profile.json
    │   ├── notes.txt
    │   └── resume.pdf
    │
    └── Cache
        ├── image.jpg
        └── temporary-file.tmp
```

The actual physical locations differ between Android and iOS.

Therefore:

> **Never assume a hard-coded physical device path will be the same everywhere.**

Use Expo APIs such as `Paths`.

---

## 1.14 Persistent vs Temporary Data

Not every file needs to live forever.

### Persistent Data

Data the application wants to keep available.

Examples:

```text
Saved note
Downloaded document
User-created file
```

### Temporary Data

Data that can be recreated or downloaded again.

Examples:

```text
Image preview
Temporary conversion output
Cache file
```

Mental model:

```text
Do I need to keep this file?

       ┌───────────────┐
       │               │
      YES              NO
       │               │
       ↓               ↓
   persistent       temporary
```

This is a purpose/lifetime decision, not a file-extension decision.

Suppose the user downloads:

The application can store it locally:

This can support:

- Saved documents
- Caching

# Part 2 — Understanding `Paths`

In Part 1 we learned:

```text
File
Directory
Path
URI
Storage
```

Now we start working with the modern Expo File System API.

The first major concept is:

```text
Paths
```

Before creating a file or directory, ask:

> **Where should it be stored?**

That is where `Paths` becomes useful.

---

## 2.1 What is `Paths`?

Import:

```tsx
import { Paths } from "expo-file-system";
```

Mental model:

```text
Paths
  ↓
"Where?"
```

`Paths` provides important storage locations and path utilities.

---

## 2.2 Why Do We Need `Paths`?

A file needs a location.

Conceptually:

```text
Location
   ↓
notes.txt
```

Possible locations:

```text
Documents/
└── notes.txt
```

or:

```text
Cache/
└── notes.txt
```

The correct location depends on the purpose and lifetime of the file.

---

## 2.3 Why Not Hard-Code Device Paths?

Do not do this:

```tsx
const path = "/some/device/folder/myfile.txt";
```

Android and iOS manage application storage differently.

Instead:

```text
Application
    ↓
Expo Paths
    ↓
Correct application location
```

Let Expo and the platform provide the correct location.

---

## 2.4 Importing `Paths`

```tsx
import { Paths } from "expo-file-system";
```

Important properties include:

```tsx
Paths.document
Paths.cache
Paths.bundle

Paths.availableDiskSpace
Paths.totalDiskSpace
```

There are also path utility methods.

---

## 2.5 Three Important Locations

For beginners:

```text
Paths.document
Paths.cache
Paths.bundle
```

Mental model:

```text
                      Paths
                        │
           ┌────────────┼────────────┐
           ↓            ↓            ↓
       document       cache        bundle
           │            │            │
         Keep       Temporary     App assets
        files          files
```

---

## 2.6 `Paths.document`

`Paths.document` represents the application's document directory.

It is a `Directory` object.

```tsx
console.log(Paths.document);
console.log(Paths.document.uri);
```

Think:

```text
Paths.document
      ↓
Application document location
```

---

## 2.7 What Belongs in `Paths.document`?

Use it for files the application should keep available.

Examples:

```text
Saved notes
User-created documents
Important downloaded documents
Application-generated files
Persistent JSON files
```

Conceptually:

```text
Paths.document
       ↓
Documents/
├── notes.txt
├── profile.json
├── resume.pdf
└── assignments/
```

Expo describes the document directory as a location whose files are safe from automatic deletion by the system.

---

## 2.8 `Paths.cache`

`Paths.cache` represents the application's cache directory.

It is also a `Directory`.

```tsx
console.log(Paths.cache);
console.log(Paths.cache.uri);
```

Mental model:

```text
Paths.cache
     ↓
Temporary / re-creatable storage
```

---

## 2.9 What is Cache?

A cache stores data temporarily so it can be reused efficiently.

Example:

```text
Internet
   ↓
Download image
   ↓
Cache
   ↓
Display image
```

The image can potentially be downloaded again.

---

## 2.10 Can Cache Files Be Deleted?

Yes.

Expo describes the cache directory as a location where files may be deleted when the device is running low on storage.

Therefore:

```text
Cache
  ↓
Do NOT assume permanent availability
```

Do not keep the only copy of an important user document in cache.

---

## 2.11 `Paths.document` vs `Paths.cache`

| `Paths.document` | `Paths.cache` |
|---|---|
| Files the application wants to keep | Temporary/re-creatable files |
| Important application files | Cached resources |
| Saved documents | Temporary downloads |
| Safer from automatic system deletion | May be deleted under storage pressure |

Decision model:

```text
Can the file be recreated/downloaded again?

        ┌───────────────┐
        │               │
       NO              YES
        │               │
        ↓               ↓
    document          cache
```

This is a simplified teaching model.

---

## 2.12 File Extension Does Not Decide Location

Consider:

```text
assignment.pdf
preview.pdf
```

Both are PDFs.

But:

```text
assignment.pdf → document
preview.pdf    → cache
```

Why?

Because **purpose and lifetime** decide the location.

> `.pdf`, `.jpg`, `.json`, etc. do not decide whether a file belongs in document or cache storage.

---

## 2.13 `Paths.bundle`

`Paths.bundle` represents the directory where assets bundled with the application are stored.

Mental model:

```text
Developer
   ↓
Build Application
   ↓
Assets included with app
   ↓
Bundle
```

Think:

```text
Paths.bundle
     ↓
Resources bundled with the application
```

This is different from runtime-created document or cache files.

---

## 2.14 `document` vs `cache` vs `bundle`

| Location | Main purpose |
|---|---|
| `Paths.document` | Files the application should keep |
| `Paths.cache` | Temporary/re-creatable files |
| `Paths.bundle` | Resources bundled with the application |

Mental model:

```text
                         Application
                              │
              ┌───────────────┼───────────────┐
              ↓               ↓               ↓
          document          cache           bundle
              │               │               │
           Keep            Temporary        Included
           files             files          with app
```

---

## 2.15 Important — These Are `Directory` Objects

This is extremely important in the modern API.

```tsx
Paths.document
Paths.cache
Paths.bundle
```

are `Directory` objects.

They are not merely arbitrary strings.

That means we can use them as parents when constructing files/directories.

---

## 2.16 Connecting `Paths` With `File`

Suppose we want:

```text
Documents/note.txt
```

Modern API:

```tsx
import { File, Paths } from "expo-file-system";

const file = new File(Paths.document, "note.txt");
```

Read it in English:

> Create a File reference for `note.txt` inside the document directory.

Mental model:

```text
new File(
    WHERE?,
    FILE NAME?
)
```

Therefore:

```tsx
new File(Paths.document, "note.txt");
```

means:

```text
WHERE?
  ↓
Paths.document

FILE?
  ↓
note.txt
```

Important:

> This creates a **File reference/object**. It does not automatically mean the physical file has been created.

---

## 2.17 Connecting `Paths` With `Directory`

Suppose we want:

```text
Documents/
└── notes/
```

We can represent it:

```tsx
import { Directory, Paths } from "expo-file-system";

const notesDirectory = new Directory(
  Paths.document,
  "notes"
);
```

Again:

```text
WHERE?
  ↓
Paths.document

DIRECTORY?
  ↓
notes
```

This creates a `Directory` reference.

The actual directory can be created later with:

```tsx
notesDirectory.create();
```

---

## 2.18 Building Nested Locations

Modern `File` and `Directory` constructors can accept path parts.

Example:

```tsx
const file = new File(
  Paths.document,
  "notes",
  "college",
  "react-native.txt"
);
```

Conceptually:

```text
Paths.document
       ↓
notes
       ↓
college
       ↓
react-native.txt
```

This avoids manually constructing platform-specific absolute paths.

---

## 2.19 Reference vs Actual Resource

Consider:

```tsx
const file = new File(
  Paths.document,
  "note.txt"
);
```

This means:

```text
"I want to work with the file at this location."
```

It does **not** automatically create the physical file.

Same idea for:

```tsx
const directory = new Directory(
  Paths.document,
  "notes"
);
```

The directory reference may exist in JavaScript even if the physical directory does not yet exist.

Check:

```tsx
console.log(file.exists);
console.log(directory.exists);
```

Then explicitly create when needed.

## 2.20 Viewing the URI

You can inspect the URI:

Now we know:


The main question becomes:

> **How do we create, inspect, list, copy, move, rename, delete, and watch folders?**

---

## 3.1 What is `Directory`?

`Directory` represents a directory/folder on the file system.

Import it:

```tsx
import { Directory, Paths } from "expo-file-system";
```

Mental model:

```text
Directory
    ↓
A reference to a folder
```

Example:

```tsx
const notesDirectory = new Directory(
  Paths.document,
  "notes"
);
```

Conceptually:

```text
Documents/
└── notes/
```

---

## 3.2 A `Directory` Object Is a Reference

This is one of the most important concepts.

When we write:

```tsx
const notesDirectory = new Directory(
  Paths.document,
  "notes"
);
```

we have created a JavaScript object representing that location.

It does not necessarily mean the physical directory already exists.

Think:

```text
new Directory(...)
       ↓
"Which directory do I want to work with?"
```

Then:

```tsx
notesDirectory.exists
```

answers:

```text
"Does that directory actually exist?"
```

---

## 3.3 Creating a Directory

To physically create the directory:

```tsx
notesDirectory.create();
```

Complete:

```tsx
import { Directory, Paths } from "expo-file-system";

const notesDirectory = new Directory(
  Paths.document,
  "notes"
);

notesDirectory.create();
```

Flow:

```text
new Directory(...)
       ↓
Directory reference
       ↓
create()
       ↓
Actual directory
```

---

## 3.4 Checking `exists`

A directory has:

```tsx
directory.exists
```

Example:

```tsx
const notesDirectory = new Directory(
  Paths.document,
  "notes"
);

console.log(notesDirectory.exists);
```

Possible result:

```text
true
```

or:

```text
false
```

Mental model:

```text
Directory
   ↓
exists?
   ↓
true / false
```

---

## 3.5 Why Check `exists`?

It prevents us from assuming that a directory is already present.

Example:

```tsx
const notesDirectory = new Directory(
  Paths.document,
  "notes"
);

if (!notesDirectory.exists) {
  notesDirectory.create();
}
```

This is useful when application setup needs to happen safely.

However, the `create()` options can also control behavior when the target already exists.

---

## 3.6 `create()` Options

The directory `create()` method supports options such as:

```text
idempotent
intermediates
overwrite
```

Example:

```tsx
directory.create({
  idempotent: true,
});
```

### `idempotent`

If `true`, creating an already-existing directory succeeds without throwing just because it already exists.

Mental model:

```text
Already exists?
       ↓
   idempotent
       ↓
"That's okay."
```

This is useful when setup code may run more than once.

---

## 3.7 `intermediates`

Suppose we want:

```text
Documents/
└── notes/
    └── college/
```

but `notes/` does not exist yet.

We can use:

```tsx
const collegeDirectory = new Directory(
  Paths.document,
  "notes",
  "college"
);

collegeDirectory.create({
  intermediates: true,
});
```

Mental model:

```text
notes/
   ↓
college/
```

If intermediate directories do not exist, the option allows them to be created.

---

## 3.8 `overwrite`

The create options also expose:

```tsx
overwrite
```

This controls whether an existing directory should be overwritten.

For beginner code, prefer understanding:

```text
idempotent
intermediates
```

first.

Be careful with destructive/overwriting operations.

## 3.16 Listing Directory Contents

One of the most important directory operations is:

```tsx

```

It returns an array containing `File` and `Directory` objects.

Example:

```tsx

console.log(contents);
```

Conceptually:

```text
notes/
├── note1.txt
├── note2.txt
└── college/
```

The result contains:

```text

File("note2.txt")
Directory("college")
```

---

## 3.17 Listing Files and Directories Separately

Because `list()` returns both `File` and `Directory`, we can distinguish them.

```tsx
const contents = notesDirectory.list();

for (const item of contents) {
  if (item instanceof Directory) {
    console.log("Directory:", item.name);
  } else {
    console.log("File:", item.name);
  }
}
```

Mental model:

```text
directory.list()
       ↓
 ┌─────┴─────┐
 ↓           ↓
File      Directory
```

This is extremely useful for file manager applications.

---

## 3.18 Listing Recursively

Suppose:

```text
Documents/
└── notes/
    ├── note1.txt
    ├── note2.txt
    └── college/
        ├── react.txt
        └── expo.txt
```

A recursive function can inspect the complete tree:

```tsx
function printDirectory(
  directory: Directory,
  indent = 0
) {
  console.log(
    `${" ".repeat(indent)}+ ${directory.name}`
  );

  const contents = directory.list();

  for (const item of contents) {
    if (item instanceof Directory) {
      printDirectory(item, indent + 2);
    } else {
      console.log(
        `${" ".repeat(indent + 2)}- ${item.name}`
      );
    }
  }
}
```

Use:

```tsx
const root = new Directory(Paths.document);

printDirectory(root);
```

Mental model:

```text
Directory
   ↓
List
   ↓
Is item a directory?
   ├── YES → List it again
   └── NO  → File
```

---

## 3.19 `list()` Error Case

If the parent directory does not exist, calling:

```tsx
directory.list()
```

can throw an error.

Therefore:

```tsx
if (directory.exists) {
  const contents = directory.list();
}
```

or use error handling:

```tsx
try {
  const contents = directory.list();
  console.log(contents);
} catch (error) {
  console.error(error);
}
```

Good file-system code expects missing resources.

## 3.31 Watching a Directory

The modern API provides:

```tsx
directory.watch(callback)
```

```tsx
const subscription = notesDirectory.watch(
```

```text

deleted
renamed
```

## 3.32 Why Would We Watch a Directory?

Imagine a file manager:

```text
Documents
│
├── note1.txt
├── note2.txt
└── assignment.pdf
```

If a file is created:

```text
new-file.txt
```

the application may want to refresh the displayed list.

Flow:

```text
File System Change
       ↓
Directory Watcher
       ↓
Callback
       ↓
Update React State
       ↓
Refresh UI
```

This is a real-world connection between:

```text
File System
     +
React Native UI
```

---

## 3.33 Removing a Watch Subscription

`watch()` returns a subscription.

Stop watching:

```tsx
subscription.remove();
```

Example:

```tsx
const subscription = notesDirectory.watch(
  (event) => {
    console.log(event.type);
  }
);

// Later
subscription.remove();
```

Mental model:

```text
watch()
  ↓
Subscription
  ↓
remove()
  ↓
Stop watching
```

In React components, cleanup is important:

```tsx
useEffect(() => {
  const subscription = directory.watch(
    (event) => {
      console.log(event.type);
    }
  );

  return () => {
    subscription.remove();
  };
}, []);
```

---

## 3.34 Directory Watch Event Types

The watcher can report events such as:

```text
created
modified
deleted
renamed
```

Example:

```tsx
const subscription = directory.watch(
  (event) => {
    switch (event.type) {
      case "created":
        console.log("Created:", event.target.uri);
        break;

      case "modified":
        console.log("Modified:", event.target.uri);
        break;

      case "deleted":
        console.log("Deleted:", event.target.uri);
        break;

      case "renamed":
        console.log("Renamed:", event.target.uri);
        break;
    }
  }
);
```

---

## 3.35 Important iOS Watcher Note

Directory watching behaves differently across platforms.

On iOS, child changes can be surfaced as a coarse `modified` event on the directory itself.

Therefore, do not build platform-sensitive logic that assumes every child-level `created`, `deleted`, or `renamed` event will always be available on iOS.

For advanced watchers, always consider platform behavior.

## 4.19 Why is `text()` Asynchronous?

Reading a file involves accessing the device's storage.

That operation may take time.

Therefore, the asynchronous API is used like:


```text

    ↓

    ↓
Device File System
    ↓
Read file
    ↓
Return content
    ↓
JavaScript
```

Because the operation is asynchronous, we use:

```tsx

```

inside an appropriate asynchronous function.

## 4.25 Copy vs Move

This distinction is important.

### Copy

```text
Original
   ↓
Duplicate
```

The original remains.

```text

    ↓ copy
```

```text

```

### Move

```text
Original
   ↓
New Location
```

The file changes location.

Example:

```text
temporary/notes.txt
        ↓ move
documents/notes.txt
```

After the move:

```text
temporary/
documents/
└── notes.txt
```

Mental model:

```text
Copy → Keep the original
Move  → Change the location
```

## 4.38 Complete Notes Example

```tsx
import { useState } from "react";
import {
  View,
  Text,
  TextInput,
  Button,
} from "react-native";

import {
  File,
  Paths,
} from "expo-file-system";

export default function App() {
  const [note, setNote] = useState("");
  const [savedNote, setSavedNote] = useState("");

  const file = new File(
    Paths.document,
    "note.txt"
  );

  const saveNote = () => {
    if (!file.exists) {
      file.create();
    }

    file.write(note);
  };

  const readNote = async () => {
    if (!file.exists) {
      setSavedNote("File does not exist");
      return;
    }

    const content = await file.text();

    setSavedNote(content);
  };

  const deleteNote = () => {
    if (file.exists) {
      file.delete();
      setSavedNote("");
    }
  };

  return (
    <View
      style={{
        flex: 1,
        padding: 20,
        justifyContent: "center",
        gap: 12,
      }}
    >
      <TextInput
        value={note}
        onChangeText={setNote}
        placeholder="Enter your note"
        style={{
          borderWidth: 1,
          padding: 10,
        }}
      />

      <Button
        title="Save Note"
        onPress={saveNote}
      />

      <Button
        title="Read Note"
        onPress={readNote}
      />

      <Button
        title="Delete Note"
        onPress={deleteNote}
      />

      <Text>
        Saved Note: {savedNote}
      </Text>
    </View>
  );
}
```

The important architecture is:

```text
TextInput
    ↓
React State
    ↓
Save
    ↓
File System
    ↓
note.txt
```

and:

```text
note.txt
    ↓
Read
    ↓
React State
    ↓
UI
```

## 4.43 Error and Failure Mindset

File operations can fail.

A good application should not assume that every operation succeeds.

Common situations include:

```text
File does not exist
Directory does not exist
Invalid path
Wrong resource type
File already exists
Insufficient storage
Access/permission issue
Read failure
Write failure
Download failure
Upload failure
```

A common JavaScript pattern is:

```tsx
try {
  // File operation
} catch (error) {
  console.error(error);
}
```

For example:

```tsx
try {
  const content = await file.text();

  console.log(content);
} catch (error) {
  console.error(
    "Failed to read file:",
    error
  );
}
```

The important mindset is:

```text
Check State
    ↓
Perform Operation
    ↓
Handle Failure
```

| Property | Meaning |
|---|---|
| `name` | File name |
| `extension` | File extension |
| `uri` | File URI |
| `parentDirectory` | Parent directory |
| `exists` | Whether the file exists |
| `size` | File size |
| `type` | MIME type |
| `creationTime` | Creation information |
| `modificationTime` | Modification information |

These properties help the application understand the current file.

## 4.47 `File` and Storage Locations

A `File` does not exist independently from a location.

For example:

```tsx
const documentFile = new File(
  Paths.document,
  "assignment.pdf"
);
```

This represents:

```text
Document Storage
      ↓
assignment.pdf
```

Another file can use cache:

```tsx
const cachedFile = new File(
  Paths.cache,
  "preview.pdf"
);
```

This represents:

```text
Cache Storage
      ↓
preview.pdf
```

The file extension is the same, but the purpose is different.

```text
assignment.pdf
    ↓
Important saved document

preview.pdf
    ↓
Temporary/re-creatable data
```

---

## 4.48 File Location Is a Design Decision

When creating a file, ask:

```text
What is this file?
        ↓
How long should it live?
        ↓
Can it be recreated?
        ↓
Where should it be stored?
```

For example:

```text
User's saved document
        ↓
document

Temporary preview
        ↓
cache
```

Therefore:

> **Storage location should be chosen based on the file's purpose and lifecycle.**

## 4.49 Complete `File` Mental Model

At this point, the complete structure should look like:

```text
Expo File System
       │
       ├── Paths
       │     │
       │     ├── document
       │     ├── cache
       │     └── bundle
       │
       ├── Directory
       │     │
       │     ├── create
       │     ├── list
       │     ├── copy
       │     ├── move
       │     ├── rename
       │     └── delete
       │
       └── File
             │
             ├── create
             ├── write
             ├── text
             ├── textSync
             ├── json
             ├── copy
             ├── move
             ├── rename
             ├── delete
             ├── info
             └── watch
```

The relationship is:

```text
Paths
  ↓
Directory
  ↓
File
  ↓
Content
```

And the file lifecycle is:

```text
Reference
   ↓
Create
   ↓
Write
   ↓
Read
   ↓
Update
   ↓
Copy / Move / Rename
   ↓
Delete
```
